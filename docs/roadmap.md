# Roadmap

目标：**每月一个小版本，每个版本一个行为**。不预告具体日期，但**每个版本的内容是预切好的**——
这份文件就是"预切好的"：先别把选项留给临头临时拍板。

## 发布纪律

1. **一个行为，一个版本**。讲不清用途就不发；不夹带"顺手改改"
2. 纵到底完成：实现 + 测试 + 文档 + `CHANGELOG` + `tag` + 校验后发布
3. 尺寸上限：**S**=文档/UI 文案/单个命令（≤ ~100 行）丨 **M**=单一行为（≤ ~200 行）丨 **L**=不进月版
4. 每个发布前必须：测试绿、`cargo audit` 无新增、CI 绿才打 tag
5. 不准改快车道：宁可一个月什么都不动，不发"半个功能"

## 下一步（按优先级）

| 版本 | 内容 | 档位 | 为什么排这个 |
|---|---|---|---|
| v0.11.0 | **备份校验**：导出加密备份后本地校验 SHA-256 | S | 防"以为备份好了其实没有"；排在恢复流程之后，能用的备份必然通过校验，部分内容会被恢复向导吸收 |

> v0.9.0 / v0.10.0 来自 [`docs/mvp.md`](mvp.md)「完成 MVP 后」清单，此前没排进版本表，容易掉队，现已并入。
> 两项底层是同一台机器：写出一对新文件、验证能打开、再替换旧文件，且都保留旧文件。

> **v0.9.0 / v0.10.0 都略超 M 档**：它们要动用户唯一的 Vault 文件，是这个应用里最危险的操作，
> 所以宁可多写：先写新的一对并**解开验证一遍**才替换旧的，任何一步失败原文件保持原样，
> 换发/恢复前的文件另外保留一份。

> **一次例外**：v0.6.0 超出了 M 档（≤ ~200 行）。原因是这个行为没法更小——
> 要拿到「可信的调用方」，就必须从管道句柄向内核问 PID、再反查进程名；
> 要把它交出去，就必须新增一个 Pipe 操作，客户端契约得同步；
> 再加上环形缓冲、CLI、`--json`、测试和文档，落地就这个体量。
> 拆得更碎也只会得到「有记录但没人能看」的半成品，所以这一次按 L 的体量发了，
> 并且把「应用内面板」单独留给 v0.7.0。

补充说明（实现时别走偏）：

- **恢复身份轮换**要重写 `vault.age` 与 `vault.identity.age` 两个文件（旧恢复文件必须真的打不开，不只是提示失效）
- **备份恢复**面对的是一对文件（`vault.age` + `.identity.age`），不是单个文件；恢复流程要先校验这对文件匹配，再落到标准位置
- **读取记录**只放内存、不落盘；只记条目名不记值；锁定时读不到；进程与 PID 由服务端核实，项目与目录是调用方自报，只能当线索

## 明确不做（边界，不会再提）

- 多机/团队同步、账号、RBAC、云同步
- 非交互解锁（CI 管道）——避免主密码出现在脚本
- 自动轮换 / 动态凭据——Vault 只存静态值
- 生成含明文密钥的配置文件
- macOS / Linux（目前只承诺 Windows）
- 代码签名（等有真实用户再说；EV/OV 见文档）

## 每月例行

- 月初选本月那一项（从上表）；其余不碰
- 月中实现；月底发版（tag → GitHub Release，先本地验证再 Publish）
- 发版后更新本表和 `CHANGELOG.md`
